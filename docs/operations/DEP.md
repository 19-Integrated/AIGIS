## PREAMBLE

The Doctrine Extension Protocol (DEP) is the meta-governance instrument of 19 Integrated. It governs how the institutional framework stack — IMP, EAF, ICC-8, AICA-5, AWOF, ILTP, CGF, ERDP, RGI-8, CAD-7, and all instruments derived from them — may be extended, amended, superseded, or retired. It answers: *By what governed process does the institution's own doctrine evolve without drifting?*

DEP is not an amendment procedure, a version control policy, or a change management checklist. It is the **constitutional amendment logic** of 19 Integrated. Without DEP, the framework stack is a closed system that cannot adapt. With an ungoverned extension process, the stack becomes arbitrary — frameworks proliferate without constitutional grounding, instruments contradict each other, and the compounding institutional intelligence that IMP is designed to build degrades into noise.

**The core insight:** A governance stack that cannot evolve is brittle; a governance stack that evolves without governance is chaotic. DEP resolves this by establishing what qualifies as a valid doctrine extension signal, how signals are evaluated, what classes of change are permitted, who may authorize each class, and how the record of doctrine evolution is maintained.

## SECTION 1: PURPOSE AND SCOPE

### Purpose

DEP ensures that:

1. **Doctrine evolves from evidence** — Extensions trace to documented signals, not preference or convenience  
2. **The stack remains constitutional** — Changes preserve ICC-8 invariants  
3. **Change is minimal** — Extensions are the minimum necessary to address the signal  
4. **Change is permanent record** — All changes are logged in IMP  
5. **Retroactive stability is preserved** — Prior objects retain governance version binding  
6. **HAN is the sole authorization authority** — No doctrine change without HAN review and approval

### Scope

| In Scope | Out of Scope |
| :---- | :---- |
| All stack instruments (ICC-8, AICA-5, AWOF, EAF, IMP, ILTP, CGF, ERDP, RGI-8, CAD-7, etc.) | Client engagement deliverables (CEF) |
| Signal identification and qualification | Business strategy or marketing |
| Change classification (4 classes) | Operational efficiency |
| Impact assessment | Technical delivery execution |
| HAN authorization | Commercial decisions |

### Governing Relationships

| Instrument | Relationship to DEP |
| :---- | :---- |

## SECTION 2: FOUNDATIONAL PRINCIPLES

| \# | Principle | Description |
| :---- | :---- | :---- |
| **P1** | **Doctrine Evolves From Evidence** | No framework, instrument, or position may be extended or amended based on preference, convenience, or commercial pressure alone. Every extension must be traceable to a documented signal. |
| **P2** | **The Stack Is a Constitutional System** | Instruments are components of a constitutional system. A change to one instrument may have downstream effects on others. DEP requires that all downstream effects be mapped before any amendment is authorized. |
| **P3** | **Minimum Necessary Change** | When a signal warrants doctrine evolution, the response is the minimum change necessary to address the signal. New frameworks are not created when an amendment to an existing instrument suffices. |
| **P4** | **Every Change Is Permanent Record** | Doctrine evolution is institutional memory. Every signal, evaluation, decision, and version change is recorded in IMP. No change is made off-record. |
| **P5** | **Retroactive Stability** | DEP changes do not retroactively alter prior engagements, decisions, or artifacts. All historical IMP objects retain their governance version binding. |
| **P6** | **HAN as Sole Authorization Authority** | No doctrine change of any class may be authorized without HAN review and approval. The AI operating architecture may identify signals, draft proposals, and conduct impact assessments — but authorization is a human accountability function that may not be delegated to AI. |

## SECTION 3: EXTENSION SIGNAL TYPES

### Overview

A valid doctrine extension process begins with a signal. Signals are the empirical inputs that justify evaluating whether doctrine evolution is warranted. There are five recognized signal types.

| \# | Signal Type | Description | Example |
| :---- | :---- | :---- | :---- |
| **1** | **Engagement Gap** | Signal arising from an active or completed client engagement where the existing framework stack produced an incomplete, ambiguous, or contradictory output. Must be documented as OEO or DRO. | Engagement reveals AICA-5 does not address a specific class of autonomous agent deployment increasingly common in the client sector. |
| **2** | **External Environment Change** | Material change in regulatory environment, technology landscape, or institutional governance context rendering existing instrument incomplete or inconsistent with current conditions. | New AI governance regulation enacted in a jurisdiction where 19 Integrated operates. Existing CEF engagement terms do not address new compliance obligations. |
| **3** | **Internal Contradiction** | Logical inconsistency between two or more instruments producing conflicting outputs when applied simultaneously to the same engagement context. | IMP's provenance chain standard and AWOF's delegation rules produce conflicting requirements for hybrid AI-human decision records. |
| **4** | **Stress-Test Failure** | Scenario stress-test against any instrument produces a failure mode the current instrument cannot govern. May be identified through client engagement, internal review, or deliberate scenario analysis. | Stress-test of EAF's Tier 4 monitoring permissions reveals scenario where AI operating architecture could infer sensitive personnel information from aggregate organizational data without explicit consent. |
| **5** | **New Capability or Domain** | New institutional capability, service domain, or operational method not governed by any existing instrument. | 19 Integrated develops a drift detection methodology. No existing instrument governs the measurement logic, threshold definitions, or alert protocols. |

## SECTION 4: SIGNAL QUALIFICATION STANDARD

### Standard

Not every observation qualifies as a DEP signal. A signal must meet the qualification standard before it enters the DEP process.

| \# | Criteria | Description |
| :---- | :---- | :---- |
| **1** | **Specificity** | The signal identifies a specific gap, contradiction, failure mode, or unaddressed domain. General observations that "the framework could be improved" do not qualify. |
| **2** | **Evidence Basis** | The signal is grounded in a documented source: an IMP object (OEO, DRO, XOO), an external regulatory text, a named stress-test scenario, or a defined new capability. |
| **3** | **Non-Redundancy** | The signal addresses something not already addressed by an existing instrument or a signal already in the DEP process. |
| **4** | **Stack Relevance** | The signal relates to the governance of 19 Integrated's institutional operating architecture, not to a specific client deliverable. Client-specific gaps are addressed through the engagement process. Signals that reveal systemic gaps in the stack are DEP signals. |

### Qualification Process

| Step | Action | Responsible | Timeline |
| :---- | :---- | :---- | :---- |
| 1 | Signal documented in IMP (as observation note on relevant OEO, DRO, or as standalone observation) | Any | Upon identification |
| 2 | Signal assessed against qualification standard | Node Steward (Ac-N5) | Within 14 days |
| 3 | If qualified → enter DEP process | Node Steward (Ac-N5) | Upon qualification |
| 4 | If not qualified → logged as observation; process ends | Node Steward (Ac-N5) | Upon determination |

### IMP Logging

| Object | Type | Content |
| :---- | :---- | :---- |
| **OEO** | `outcome_type: "signal_identification"` | Signal documented |
| **DRO** | `decision_type: "framework_selection"` | Qualification determination |

## SECTION 5: CHANGE CLASSIFICATION

### Overview

Every proposed doctrine change is classified into one of four classes. The class determines the authorization requirements, the impact assessment scope, and the IMP recording standard.

| \# | Class | Definition | Examples |
| :---- | :---- | :---- | :---- |
| **I** | **Clarification** | Resolves ambiguity, corrects error, or adds specificity to an existing instrument without altering substantive rules, scope, or governing relationships | Adding missing field definition to IMP object type; clarifying ambiguous term in EAF's intake doctrine; correcting internal cross-reference error; adding example to illustrate existing rule |
| **II** | **Amendment** | Modifies substantive rules, scope, permissions, or governing relationships of an existing instrument without altering foundational architecture or constitutional position | Adding new trust tier condition to EAF; expanding IMP's canonical object types with new field; revising AICA-5's maturity scoring dimensions; updating AWOF's delegation authority thresholds; adding new HAN trigger condition to EAF's trigger register |
| **III** | **Structural Extension** | Adds a new instrument to the canonical stack, fundamentally restructures an existing instrument's architecture, or alters governing relationships between instruments | Admitting new instrument to canonical stack; restructuring IMP's canonical object types (adding or retiring object type); altering EAF's trust tier architecture; redefining governing relationships between existing instruments; extending stack to new service domain or operational context |
| **IV** | **Constitutional Amendment** | Change to ICC-8 or to any instrument's relationship to ICC-8, or any change that alters fundamental constitutional architecture | Amending any ICC-8 invariant; changing what constitutes a constitutional violation; altering relationship between ICC-8 and any other instrument; redefining primitive layer (Trust/Memory/Action) architecture; any change that would alter foundational product thesis of 19 Integrated |

## SECTION 6: IMPACT ASSESSMENT REQUIREMENTS

| Class | Assessment Scope | Documentation |
| :---- | :---- | :---- |
| **Class I** | Affected instrument only | DRO per determination |
| **Class II** | All referencing instruments; all affected instruments must be identified and consequential amendments mapped | DRO per determination |
| **Class III** | Full stack; every instrument in canonical stack assessed for impact; instruments requiring consequential amendments, version notation only, or no impact identified | GAO impact assessment document \+ DRO per determination |
| **Class IV** | Full constitutional impact assessment; every instrument in canonical stack; every active client engagement; every IMP object produced under prior constitutional state; assessment identifies whether prior objects remain valid under proposed change or require reissuance | GAO constitutional impact assessment document \+ DRO per determination |

## SECTION 7: DEP PROCESS FLOW

SIGNAL IDENTIFICATION  
└── Signal observed (engagement gap, external change, contradiction,  
    stress-test failure, or new capability)  
└── Signal documented in IMP (as observation note on relevant OEO,  
    DRO, or as standalone CRO)

SIGNAL QUALIFICATION  
└── Signal assessed against qualification standard  
    (specificity, evidence basis, non-redundancy, stack relevance)  
└── Qualified → enter DEP process  
└── Not qualified → logged as observation; process ends

CHANGE CLASSIFICATION  
└── Proposed change classified (Class I / II / III / IV)  
└── Classification documented as DRO

IMPACT ASSESSMENT  
└── Class I: affected instrument only  
└── Class II: all referencing instruments  
└── Class III: full stack  
└── Class IV: full constitutional assessment  
└── Impact assessment documented (DRO for each determination;  
    GAO for Class III and IV assessment documents)  
DELIBERATION PERIOD  
└── Class I: none required  
└── Class II: minimum 48 hours  
└── Class III: minimum 7 days  
└── Class IV: minimum 30 days \+ 8-scenario stress test

HAN REVIEW AND AUTHORIZATION  
└── HAN reviews signal, classification, impact assessment,  
    and proposed change  
└── HAN authorizes / modifies / rejects  
└── Authorization documented as DRO (han\_review\_flag: true,  
    han\_outcome: approved / modified / rejected)

INSTRUMENT REVISION  
└── Affected instrument(s) revised  
└── Version increments applied per classification  
└── Governing framework version map updated

IMP RECORDING  
└── All DEP objects recorded per classification standard  
└── Governance version binding updated across all affected objects  
    for forward-dated engagements

NOTIFICATION  
└── Active engagements at affected trust tiers notified of  
    version change in their ECO  
└── No retroactive alteration to historical objects

## SECTION 11: DEP SELF-REFERENCE PROVISION

### Rule

DEP governs its own amendment. Changes to DEP are subject to DEP's own process.

| Change Scope | Classification |
| :---- | :---- |
| Clarification of DEP language | Class I |
| Amendment to signal types, qualification standard, or change classification definitions | Class II |
| Structural change to DEP process flow | Class III |
| Any change that alters DEP's relationship to ICC-8 | Class IV |

### Prohibition

DEP may not be amended in a manner that reduces the authorization requirements for any change class. Authorization requirements may only be increased through DEP amendment, never decreased, except through a Class IV constitutional amendment with full deliberation.
